Agent × 大模型的上下文 × Skill

1三者角色定位

先各就各位：谁在干活、谁提供干活的环境、谁教它怎么干。

概念本质是什么解决什么问题生命周期类比
Agent
执行主体		 把 LLM 放进"思考→行动→观察"循环的系统 让模型从"一问一答"升级为"自主完成多步任务" 随任务创建，任务结束即终止 新来的全能实习生（发动机）
上下文
信息环境		 每次推理时模型能看见的全部信息集合（受窗口容量约束） 模型没有真记忆——上下文是它唯一的信息来源 随每次请求重建，内容动态变化 实习生面前的工作台（摊着什么就只能用什么）
Skill
知识资产		 打包成文件夹的程序性知识（SKILL.md + 脚本 + 参考资料） 把"某次会做"沉淀为"每次都会做"的可复用方法 长期存在于文件系统，人工/半自动迭代 档案柜里的岗位 SOP 手册库
一句话抓住三者关系：Agent 在上下文这台"工作台"上循环干活；上下文决定了它此刻能做多好；Skill 是档案柜里的手册，在正确的时机被抽出来摊上工作台，把一次性的聪明变成可复制的专业。上下文管"现在"，Skill 管"一直"，Agent 负责把两者变成产出。

3重点一：大模型的上下文如何影响 Agent 的运行

Agent 的每一步决策都发生在上下文里——上下文的质量、容量与组织方式，直接决定了 Agent 能做多好、做多久、多贵。

五个影响维度

维度上下文如何起作用对 Agent 运行的具体影响
① 决策质量 上下文是 Agent 决策的唯一信息源：目标、规则、工具结果全部经由它进入 关键信息缺失或被噪声淹没 → 思考（Thought）环节就错了方向，后续整个循环在错误路线上空转。上下文质量 = 决策质量的天花板
② 循环寿命 窗口容量有限，而循环每转一圈都追加历史与工具结果 长任务必然触碰窗口上限 → 必须中断去压缩（compact）或外存，上下文管理节奏直接限定 Agent 能连续干多久
③ 成本与速度 每轮推理都携带全量上下文重新计算（KV Cache 只能缓解重复前缀） 循环 × 膨胀 = 成本二次增长：第 30 轮的单步成本远高于第 1 轮。上下文失控的 Agent 又慢又贵
④ 记忆与连贯 Agent 的"短期记忆"就住在上下文里（对话历史 + 中间结果） 压缩过度 → 丢关键约束，行为前后矛盾；不压缩 → 信噪比下降、注意力稀释。上下文工程就是 Agent 的记忆力管理
⑤ 感知通道 工具结果、RAG 片段、子代理汇报，都必须经过上下文才能被模型"看见" 上下文是 Agent 与真实世界之间唯一的接口——灌进垃圾，决策就基于垃圾（garbage in, garbage out）

图 2 · Agent 运行时与上下文的两个持续博弈：容量博弈（压缩时机）与质量博弈（信噪比管理）。Agent 框架的核心复杂度几乎都花在这两处。
工程启示：给 Agent 做优化时，优先级通常是——先把上下文里的垃圾清掉（工具结果截断、按相关性注入），再谈换更大窗口或更强模型。上下文的组织方式，常常比模型本身更影响 Agent 表现。

4重点二：Skill 如何沉淀可复用任务知识

Agent 每次任务结束，经验会随上下文一起消失——Skill 是打破这个"失忆循环"的沉淀机制。

为什么需要沉淀：Agent 天生"健忘"

一次调通某个复杂流程（比如把 HTML 高保真转成 Word）的过程，往往要试错好几轮——这些来之不易的经验，全部存在于当次会话的上下文里，任务结束即蒸发。下次遇到同类任务，同一个 Agent 又从零试错。Skill 的作用就是把"会做"显式化为"做法"：把成功路径提炼成 SKILL.md，写入技能目录，让未来的每次执行都能站在过去的经验上。

沉淀前 vs 沉淀后

对比维度无 Skill（每次裸跑）有 Skill（知识沉淀）
知识存在哪单次会话的上下文里，任务结束即消失文件系统中的 SKILL.md + 脚本，跨会话持久
下次怎么复用靠人重新写提示词，或 Agent 重新试错description 自动路由 → 正文注入上下文，零重启成本
质量稳定性随模型状态、措辞波动，看运气按固定 SOP 执行，输出可预期、可审计
经验归谁困在某次对话记录里，人走茶凉进 git、进技能市场，团队与跨平台共享
迭代方式无法迭代（经验已蒸发）执行反馈 → 修订 SKILL.md → 版本化管理，越用越准

图 3 · 知识沉淀闭环：把"一次性的聪明"炼成"可复制的专业"。第⑤步经上下文完成注入——Skill 对 Agent 的影响，最终都要通过上下文这块工作台兑现。
关键洞察：Skill 沉淀的知识最终仍要流经上下文才能生效——它不改变模型的参数，而是改变"模型每次能看见什么"。如果说上下文工程管的是"这次桌面怎么摆"，Skill 就是把摆桌经验写成手册，让每次开桌都直接摆对。

5完整闭环：一次任务中的三重奏

把两条线索（上下文驱动运行、Skill 沉淀知识）放进同一次任务的时序里。

sequenceDiagram
    participant U as 用户
    participant A as Agent
    participant C as 上下文（工作台）
    participant S as Skill 技能库
    U->>A: 下达任务（如：生成某概念学习资料）
    A->>C: 任务目标 + 系统提示进入上下文
    C-->>A: 第 1 轮：基于现有信息规划
    A->>S: 发现"该怎么做"缺方法知识 → 路由匹配
    S-->>C: 命中 SKILL.md → 正文注入（8 模块规范）
    A->>C: 循环执行：检索/写文件/自检，历史持续追加
    C-->>A: 窗口吃紧 → 触发压缩（compact），保留关键约束
    A->>C: 全程决策与观察都读/写上下文
    A->>U: 交付结果
    A->>S: 新经验 → 修订 SKILL.md（沉淀回路）
    Note over C,S: 上下文是"运行时"（任务结束即清空）
Skill 是"持久层"（跨任务存活与迭代）
图 4 · 时序视角：Agent 全程工作在上下文之上；Skill 在"缺方法"时注入、在"有经验"时回收。上下文解决运行的当下，Skill 积累组织的长期。
阶段上下文在做什么Skill 在做什么Agent 在做什么
任务启动重建：装入系统提示、工具定义、目标待命：所有手册只有封面摘要在场规划第一轮行动
遇到方法缺口扩容：注入匹配到的 SKILL.md 正文路由命中，手册被"翻开"按 SOP 调整执行路线
循环执行持续膨胀：历史、工具结果累积；超限则压缩脚本被执行，参考文档被按需查阅思考→行动→观察迭代
任务结束清空（工作台收拾干净，经验蒸发风险）回收：把本次新经验写回手册终止并交付

6关系速查表

把三份概念资料（agent.html / llm-context.html / skill.html）的关系收进一张表。

问一句Agent 的回答上下文的回答Skill 的回答
你是系统里的什么角色？干活的执行主体干活的信息环境教干活的知识资产
你的状态持续多久？一个任务的周期一次请求的瞬间长期存活、持续迭代
你不存在会怎样？任务只能一问一答，无法多步自治模型失明失聪，什么都做不了每次都从零试错，质量靠运气
你的失效会怎样？循环失控：重复、跑偏、不收敛决策劣化：遗忘、串扰、成本爆炸路由失灵或手册过期，形同虚设
你优化的一句话纲领设计好循环与护栏管好工作台：选、压、写、隔写好手册与封面摘要（description）
收束成一句话：Agent 是用上下文干活的人，Skill 是喂上下文养料的手册库——上下文决定 Agent 此刻的上限，Skill 决定它跨时间的成长。
