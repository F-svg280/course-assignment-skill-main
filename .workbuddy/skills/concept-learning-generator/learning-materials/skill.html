1概念个人解释

用自己的话讲清楚 Skill 是什么，并说明比喻与概念的对应关系。

我的解释：大模型是通才，但通才缺两样东西：专业岗位的"怎么做"（公司特有的流程、规范、坑点）和可复用的执行包（脚本、模板、参考案例）。Skill（Agent Skills / SKILL.md 范式）就是解决这个问题的产物：把某个领域的知识整理成一个文件夹——里面一本主手册（SKILL.md）加若干附件（脚本、参考资料、模板），放进 AI 的技能目录。AI 平时只记住每本手册封面上的摘要（几十个 token 的 description），一旦任务匹配，才把手册抽出来读，需要时再执行附带的脚本。

我认为 Skill 概念最精髓的一点是按需展开：它不是把知识一股脑塞进上下文，而是像图书馆一样——目录常驻、正文按借阅、附件按页码翻。这让"装 100 个技能"和"装 1 个技能"对日常对话的上下文占用几乎一样。

比喻：Skill 是给 AI 配的"岗位 SOP 手册 + 工具包"。新员工（AI）入职时不需要背下全公司所有岗位的操作手册，只需要知道档案柜里有哪些手册、各管什么事；接到出纳的活儿，就抽出《出纳手册》按步骤来，手册附录里还有现成的 Excel 模板（脚本）可以直接用。

比喻中的档案柜

一句话记忆：Tool 给 AI "能做什么"的手，Skill 给 AI "该怎么做"的 SOP——写好一本手册，通才立刻变专家。

2核心机制组成

一个 Skill 的文件结构、三级渐进披露的加载机制，以及它为什么省上下文。

① 文件结构：一个文件夹就是一本手册

my-skill/
├── SKILL.md          # 必须。YAML 元数据(name/description) + 正文指令
├── scripts/          # 可选。可执行脚本（如格式转换、数据处理）
│   └── convert.py
├── references/       # 可选。按需查阅的参考文档（API 说明、规范、案例）
│   └── api-details.md
└── assets/           # 可选。静态资源（模板、字体、样板文件）

SKILL.md 的开头是 YAML frontmatter，其中 description 是整个机制的"路由器"——AI 靠它判断当前任务是否匹配这个技能：

---
name: pdf
description: 读取、创建、合并 PDF 文件。触发场景：处理 PDF、提取文本、合并拆分。
---   ← 以上为元数据（常驻上下文），以下为正文（触发后加载）
# PDF 处理技能
1. 读取 PDF 文本时优先使用 scripts/extract.py ...

渐进披露：三级加载，上下文按需付费

运行链条：description 写得好坏 = 路由准不准

  • 触发：AI 拿到任务 → 扫描所有技能的 description → 判断是否相关。description 太泛会误触发，太窄会漏触发——它是 Skill 唯一的"广告位"
  • 执行：正文指令进入上下文后，等同于给模型"临时加了一段专家提示"；脚本由运行环境执行（有权限边界），输出回到上下文
  • 可移植：整个范式只是文件夹约定，不含私有 API——同一套技能目录可跨支持该范式的平台使用，也适合放进 git 团队共享
工程师视角的一句总结：Skill 是"提示词工程"的文件化升级——把散落的 prompt 沉淀为有目录、可版本管理、按需加载的知识包。

3应用场景

Skill 在真实产品与团队中的用法，以及什么时候它不是答案。

典型应用

  • 文档处理技能包：Claude Code / Claude 应用内置 pdf、xlsx、docx 等官方技能——正文写处理流程，scripts/ 带现成脚本，用户一句话"帮我合并这三个 PDF"即触发。
  • 个人工作流沉淀：把"每周写周报"的固定套路（数据来源、模板、语气要求）做成个人技能，AI 每周自动按 SOP 产出，质量不再随提示词随意波动。
  • 企业 SOP 技能化：把财报分析流程、品牌文案规范、客服话术手册封装成技能，新 AI 助手"入职即上岗"——知识沉淀在文件里而不是某个员工的提示词收藏夹里。
  • 项目级团队共享：技能目录放进仓库（如 .workbuddy/skills/），随 git 分发，团队所有人（和人+AI 组合）用同一套作业规范——本项目正在实践的用法。
  • 学术溯源——技能库思想：Voyager 在 Minecraft 中让 Agent 把学会的技能写成代码存入技能库、按需检索复用，是"能力沉淀为可检索资产"的经典学术验证。
不适合的场景（反例边界）：① 需要实时外部数据或调用私有系统——那是连接器（如 MCP）的活，Skill 只是静态知识；② 单一固定 API 调用——直接注册 Tool 更简单，包一层 Skill 纯属绕路；③ 频繁变化的动态知识——技能是手动维护的文件，时效性内容会悄悄过期；④ 无触发规律的随口问答——靠 description 路由的路由器接不住"随机聊天"。

4易混淆边界

最容易混的三组概念，一组口诀收尾。

组一：Skill vs Tool（说明书 vs 工具）

差异维度Skill（知识包）Tool（工具）
本质程序性知识：怎么做事的文档+脚本能力接口：可直接调用的函数/API
形态文件夹（Markdown 为主）注册的函数签名（JSON Schema）
上下文占用渐进披露、按需加载工具定义通常常驻上下文
关系Skill 正文里可以指导模型使用 Tool；Tool 不需要知道 Skill 存在

组二：Skill vs MCP / 连接器（说明书 vs 供货渠道）

差异维度SkillMCP / 连接器
解决什么"怎么做事"（知识、流程、规范）"接到哪里"（外部系统的标准化接入）
形态文件约定（文件夹）协议 + 服务端（实时通信）
时效性静态文档，手动维护实时读写外部系统的活数据
关系互补：一本"操作 GitHub 的手册"（Skill）+ 一条 GitHub 连接（MCP），配合使用威力最大

组三：Skill vs Prompt Template（提示词模板）

差异维度SkillPrompt Template
结构多级文档 + 脚本 + 资源单段带占位符的文本
触发方式AI 依据 description 自主路由人手动选用、填空
可组合性可带脚本执行、可互相引用独立使用，无加载机制
判断口诀："Tool 是锤子，Skill 是木工手册，MCP 是五金店供货渠道。"缺能力加 Tool，缺方法写 Skill，缺数据接 MCP。接到任务先问一句：AI 是"不会干"（缺 Tool）还是"不知道怎么干好"（缺 Skill）？

7核心思考题

开放题，没有标准答案；附思考提示。

T1 · Skill 与 RAG 的哲学分野：两者都是"把知识按需放进上下文"，一个靠意图路由（description 匹配），一个靠相似度检索（向量匹配）。程序性知识（how-to）和事实性知识（what）为什么适合不同的路由方式？边界案例（如"处理某种罕见文件格式"）该归谁管？
思考提示：RAG 的检索单元是"片段"，Skill 的检索单元是"整本手册+可执行附件"；想想"知识是否需要配套动作（脚本）"这条判据。
T2 · 路由的脆弱性：一个技能装了半年从未被触发过，可能有哪些原因？如何系统性地测试和调试 description 的触发可靠性？
思考提示：往三个方向找——description 太窄（缺触发词）、被邻居技能"截胡"（语义重叠）、任务措辞从未落在触发词上；测试可构造正例/反例任务清单批量验证。
T3 · 技能的安全边界：从市场安装第三方 Skill，本质上等于"允许一段别人写的指令在匹配时注入你的上下文"。这带来哪些风险（提示注入、恶意脚本、供应链）？一个技能市场应该设计哪些防线？
思考提示：把 Skill 类比成"软件包管理器里的包"——历史上 npm/PyPI 的供应链攻击剧本会怎么重演？想想静态审查（签名、扫描）、运行时隔离（脚本沙箱）、权限最小化三层。

8自测问题

先自己作答，再对照答案。难度递增。

Q1（识记）一个标准 Skill 文件夹的最小必需内容是什么？各可选目录放什么？
答案：必需：SKILL.md（YAML frontmatter 含 name/description + Markdown 正文指令）。可选：scripts/（可执行脚本）、references/（按需查阅的参考文档）、assets/（模板等静态资源）。（对应模块 2-①）
Q2（识记）渐进披露的三个级别分别是什么？每级的内容何时进入上下文？
答案：L1 元数据（name+description）常驻上下文，负责路由；L2 SKILL.md 正文在任务匹配后加载；L3 references/scripts 等附件在执行过程中按需读取/运行。占用与"当前任务"成正比，而非与"已装技能数"成正比。（对应模块 2）
Q3（理解）为什么说 description 是"整个 Skill 机制的路由器"？写得太泛或太窄各有什么后果？
答案：AI 完全靠 description 判断当前任务是否匹配该技能——正文再好，路由失败就永远不会被读。太泛：无关任务误触发，污染上下文甚至带偏行为；太窄：该触发的任务漏触发，技能形同虚设。（对应模块 2、思考题 T2）
Q4（辨析）"我给 AI 写了一份《Python 数据清洗规范》文档放进技能目录，所以我现在有了一个 Tool。"这句话错在哪？
答案：混淆了 Skill 与 Tool。那份文档是程序性知识=Skill（教 AI 怎么做）；Tool 是注册成函数签名的能力接口（如代码执行器本身），可被直接调用。两者是互补关系：Skill 正文可以指导 AI 如何使用 Tool。（对应模块 4 组一）
Q5（应用）三个需求分别该用 Skill、Tool 还是 MCP？① 让 AI 能查询公司内部工单系统；② 让 AI 会按公司规范写品牌周报；③ 让 AI 能执行 Python 做数据计算。
答案：① MCP/连接器（需要实时接入外部私有系统）；② Skill（静态流程知识，无需外部连接）；③ Tool（能力接口，注册代码执行函数即可）。口诀：缺数据接 MCP，缺方法写 Skill，缺能力加 Tool。（对应模块 4 口诀）
Q6（应用）为"把会议录音转写并整理成纪要"这个技能写一条合格的 description。
答案（示例）："会议录音转写与纪要整理技能。将音频/视频转写为文字，按模板整理为含决议、待办的会议纪要。触发场景：会议录音、转写、纪要、会议记录、action items。"要点：动词+名词的具体场景词、涵盖用户可能的多种说法、不含无关泛词。（对应模块 2、学习目标 4）
Q7（深度·面试）公司要把客服团队三年的处理经验技能化。请给出完整方案：结构设计、路由可靠性保障、权限与安全、迭代机制。
答案要点：① 结构：按问题域拆分技能（退款/物流/投诉升级），SKILL.md 写决策流程，references/ 放政策原文，scripts/ 放工单查询等可执行动作；② 路由：用历史真实工单构造触发测试集，批量验证命中/误触率，迭代 description；③ 安全：脚本最小权限（只读工单系统+白名单动作）、人工确认高危操作（退款执行）、技能入库前审查（供应链防护）；④ 迭代：把新案例沉淀回 references/，季度清理过期政策——技能是"活文档"。（综合模块 2/3 与思考题 T3）
